# Лабораторна робота №2: Інвертований індекс (проєкт `findex`)

## Опис
Другий етап розробки пошукового рушія `findex`. В рамках цієї лабораторної роботи реалізовано побудову інвертованого індексу, серіалізацію структур даних на диск та систему Boolean-пошуку (оператор AND) для знаходження документів за запитом.

## Архітектура та оптимізація
Для забезпечення ефективної роботи з великими текстами було застосовано такі рішення:
* **Оптимізація пам'яті:** Класи `Posting` (ідентифікатор документа та частота терміна) та `DocMeta` реалізовані через декоратор `@dataclass(frozen=True, slots=True)`. Використання `slots` дозволило відмовитись від створення словників `__dict__` для кожного об'єкта, що заощадило сотні мегабайтів оперативної пам'яті.
* **Однопрохідна обробка:** Підрахунок частоти слів виконується через `collections.Counter`, який ліниво споживає генератор токенів, уникаючи завантаження всього тексту документа в пам'ять.
* **Структура індексу:** Використовується `collections.defaultdict(list)`, де ключами є терми, а значеннями — списки постінгів, автоматично відсортовані за `doc_id`.

## Серіалізація та безпека
Збереження та завантаження побудованого індексу на диск реалізовано за допомогою вбудованого модуля `pickle`.

## Рушії пошуку (Boolean AND)
Реалізовано два підходи до перетину списків документів:
1. **Алгоритм `merge` (Два вказівники):** Класичний підхід, який послідовно порівнює два відсортовані масиви `doc_id` за час $O(N+M)$.
2. **Алгоритм `set` (Множини):** Використовує вбудовану оптимізовану (на рівні мови C) структуру даних `set` у Python.

## Результати та метрики продуктивності
Тестування проводилося на дамп-файлі Вікіпедії (1 великий документ, 7.8 млн слів).

| Метрика | Значення |
| --- | --- |
| **Час побудови індексу** | ~13.51 сек |
| **Пікова пам'ять (Побудова)** | 118.36 MB |
| **Розмір індексу на диску (`index.bin`)** | 16 MB |
| **Унікальних термів у словнику** | 442 172 |
| **Пікова пам'ять (Завантаження та пошук)** | 170.51 MB |
| **Час завантаження індексу (`merge` / `set`)** | 2.6378 сек / 2.7027 сек |
| **Час пошуку (`merge / set`)** | 0.000025 сек / 0.000017 сек |

*Примітка: Оскільки корпус складався з одного великого документа, час пошуку для обох рушіїв є миттєвим (масиви `doc_id` для перетину містять лише один елемент). Рушій `set` показав трохи вищу швидкість завдяки оптимізаціям вбудованих множин на рівні мови C.*
