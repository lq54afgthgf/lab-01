# Лаб 7. Пошук у вебі: FastAPI, Pydantic і публічна адреса

**Публічна адреса:** https://lab-01-edfh.onrender.com

## Опис
У цій лабораторній роботі реалізовано веб-інтерфейс та HTTP API для пошукового рушія на базі FastAPI. Додано веб-сторінку результатів (Jinja2), валідацію вхідних даних (Pydantic), ізольовані тести (`TestClient`) та проведено пакування у двохетапний Docker-образ без root-прав із подальшим розгортанням на хмарній платформі Render.

## Що зроблено в межах проєкту
* **HTTP API та Веб-інтерфейс (FastAPI + Jinja2):** Створено головну веб-сторінку з формою пошуку (`GET /`) та JSON-ендпоінт (`GET /search`) для програмної взаємодії з інвертованим індексом.
* **Валідація та типізація (Pydantic):** Описано суворі схеми запитів і відповідей (`SearchResponse`, `SearchResult`), налаштовано валідацію query-параметрів (перевірка порожніх рядків та лімітів видачі) і коректну обробку помилок (`422 Unprocessable Entity`, `503 Service Unavailable`).
* **Керування життєвим циклом (`lifespan`):** Реалізовано одноразове завантаження бінарного індексу (`index.bin`) у пам'ять під час старту сервера через змінну оточення `INDEX_PATH`.
* **Розширення CLI (Typer + Uvicorn):** Додано команду `findex serve` з підтримкою налаштування порту (`--port`) та кількості робочих процесів (`--workers`).
* **Автоматизоване тестування (`TestClient`):** Написано інтеграційні тести для перевірки HTML-рендерингу, JSON-відповідей та граничних випадків без необхідності підняття реального мережевого сокета.
* **Контейнеризація (Multi-stage Docker):** Розроблено оптимізований двохетапний `Dockerfile` із використанням пакетного менеджера `uv` (на базі `python:3.13-slim-bookworm`), налаштовано `.dockerignore` та запуск від імені непривілейованого користувача (`appuser`).
* **Хмарний деплой та бенчмаркінг:** Сервіс розгорнуто на платформі Render і протестовано під навантаженням за допомогою утиліти `oha` у п'яти різних конфігураціях.

## Навантажувальне тестування (oha)

Тестування проводилося командою `oha -n 200 -c 20`:

| Режим | Запитів за секунду (RPS) | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| 1 воркер (`async def`) | 2431.59 | 6.78 | 16.43 | 17.95 |
| 1 воркер (`def`) | 1852.90 | 9.67 | 19.77 | 20.87 |
| 4 воркери (`async def`) | 497.55 | 42.03 | 44.00 | 44.84 |
| 4 воркери (`def`) | 498.99 | 42.01 | 43.98 | 44.77 |
| Розгорнутий сервіс (Render) | 76.49 | 215.65 | 352.84 | 684.04 |

### Аналіз продуктивності (GIL, потоки, процеси, мережа)
* **Де винен GIL (`async def`):** Пошук і ранжування документів — це процесорно-залежна (CPU-bound) задача. Використання `async def` виконує обчислення безпосередньо в головному потоці. Через Global Interpreter Lock (GIL) це блокує асинхронний цикл подій (Event Loop) — сервер не може приймати нові з'єднання, поки не завершить поточний пошук. Локально на 1 воркері `async def` показав вищий RPS лише через малий розмір тестового індексу, де накладні витрати на передачу задачі в пул потоків перевищили час самого пошуку.
* **Де допоміг пул потоків (`def`):** FastAPI автоматично делегує синхронні `def` маршрути у зовнішній пул потоків (`threadpool`). Хоча GIL не дозволяє виконувати Python-байткод паралельно на кількох ядрах у межах одного процесу, головний потік із Event Loop залишається вільним і миттєво приймає нові вхідні запити. На 4 воркерах режим `def` випередив `async def` (498.99 проти 497.55 RPS) та показав трохи менші затримки p50–p99.
* **Де допомагають кілька процесів (4 воркери):** Запуск Uvicorn із параметром `--workers 4` створює 4 незалежні процеси ОС, кожен із власним інтерпретатором Python та окремим GIL. На великих індексах це єдиний спосіб задіяти кілька ядер процесора для справжнього паралельного виконання CPU-bound задач. На малій тестовій вибірці у 200 запитів накладні витрати ОС на розподіл сокетів між процесами знизили загальний RPS до ~498, проте зробили розподіл часу відповіді максимально рівномірним (різниця між p50 та p99 становить лише ~2.7 мс).
* **Вплив хмарного середовища (Render):** Зниження RPS до 76.49 та зростання p50 до 215.65 мс зумовлені мережевою затримкою (RTT до дата-центру Render та TLS-рукостискання займають у середньому ~63 мс) та обмеженнями безкоштовного тарифу за CPU.

## Інструкція зі встановлення та використання

### 1. Підготовка середовища
Клонуйте репозиторій та встановіть залежності за допомогою пакетного менеджера `uv`:
`bash`
git clone https://github.com/lq54afgthgf/lab-01.git
cd lab-01
uv sync

### 2. Побудова пошукового індексу (якщо index.bin відсутній)

Індексація директорії з текстовими документами:
`bash`
uv run python -m findex.cli build ./data --output index.bin

### 3. Локальний запуск веб-сервера

Вкажіть шлях до файлу індексу через змінну оточення INDEX_PATH та запустіть сервер:
`bash`
**Запуск з 1 воркером (за замовчуванням)**
INDEX_PATH=index.bin uv run python -m findex.cli serve --port 8000

**Запуск у багатопроцесорному режимі (4 воркери)**
INDEX_PATH=index.bin uv run python -m findex.cli serve --port 8000 --workers 4


### 4. Запуск у Docker-контейнері

Збірка образу та запуск контейнера з монтуванням локального файлу індексу:
`bash`
sudo docker build -t findex .
sudo docker run -p 8000:8000 -v "$(pwd)/index.bin":/app/index.bin -e INDEX_PATH=/app/index.bin findex

### 5. Використання сервісу

    Веб-інтерфейс: відкрийте у браузері http://127.0.0.1:8000/ (або https://lab-01-edfh.onrender.com/).

    JSON API: виконайте GET-запит до ендпоінту /search:
`bash`
curl "http://127.0.0.1:8000/search?q=test&k=5"

    Інтерактивна документація (Swagger UI): доступна за адресою http://127.0.0.1:8000/docs.
