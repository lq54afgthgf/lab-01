### 3. Семантичний та гібридний пошук (`all-MiniLM-L6-v2` + RRF)
Команда `findex embed` ділить документи на фрагменти по 200 слів із перекриттям 40 слів, обчислює 384-вимірні ембединги моделлю `all-MiniLM-L6-v2`, виконує L2-нормалізацію та зберігає матрицю у `.embeddings.npy` і `.chunks.npy`.
* У режимі **`mode=semantic`** вектор запиту множиться на матрицю фрагментів (`sem_index.embeddings @ q_vec`), а кожному документу зараховується бал його найкращого фрагмента через `np.maximum.at`.
* У режимі **`mode=hybrid`** результати BM25 і семантичного пошуку об'єднуються за формулою **Reciprocal Rank Fusion (RRF)**: $\text{RRF}(d) = \sum_{m \in \{\text{bm25}, \text{sem}\}} \frac{1}{60 + \text{rank}_m(d)}$.

## Зведені виміри з Лабораторних робіт №1–7

### Лаб 1. Правила токенізації та порівняння Жадібний (Greedy) vs Лінивий (Lazy) підхід

#### Правила токенізації
* **Unicode-нормалізація:** `NFC` (зведення складених символів до єдиного, наприклад, `й` + `̆` -> `й`).
* **Регістр:** Усі слова зведені до нижнього регістру через `casefold()`.
* **Фільтрація:** Зберігаються літери, цифри, а також дефіси та апострофи всередині слів (наприклад, `комп'ютер`, `будь-ласка`). Пунктуація видаляється.

#### Порівняння: Жадібний (Greedy) vs Лінивий (Lazy) підхід
Під час розробки було проаналізовано дві стратегії обробки текстів. Вибір зроблено на користь лінивого підходу, оскільки він єдиний дозволяє працювати з дампами, розмір яких перевищує обсяг оперативної пам'яті:

| Характеристика | Жадібний підхід (Greedy) | Лінивий підхід (Lazy — наша реалізація) |
| :--- | :--- | :--- |
| **Споживання пам'яті** | $O(N)$ — завантажує весь гігабайтний файл у RAM. | $O(1)$ — пам'ять витрачається лише на поточну статтю/блок. |
| **Ризик OOM (Out of Memory)** | Високий. Скрипт впаде з помилкою пам'яті при обробці великого дампу. | Відсутній. Програма стабільно обробляє файли будь-якого розміру. |
| **Початок обробки** | Довга пауза (чекає повного завантаження файлу в пам'ять). | Миттєво (починає віддавати токени з першої прочитаної лінії). |
| **Реалізація в Python** | `.read()`, `.split()`, зберігання результатів у списках `[]`. | Ітерація по файлу `for line in f:`, використання `yield`. |

**Аналіз використання пам'яті:** У «жадібному» підході пам'ять витрачається на завантаження всього масиву тексту через `f.read()` та створення гігантського списку всіх знайдених токенів одночасно через метод `re.findall()`. У «лінивому» конвеєрі ми читаємо файл по одному рядку (`for line in f`), а токенізатор віддає слова по одному через `re.finditer()`. У пам'яті одночасно перебуває лише один рядок тексту, а єдина структура, яка накопичує дані і споживає пам'ять — це агрегатор `Counter` (словник частот термів).

#### Три Sanity-Check перевірки рейтингу (BM25 vs TF-IDF)
Експериментальна перевірка властивостей формули ранжування `BM25(k1=1.5, b=0.75)`:

| № | Перевірка (гіпотеза) | Умови експерименту | Результат `BM25` | Пояснення фізики формули |
| :-: | :--- | :--- | :--- | :--- |
| **1** | **Рідкісний термін вище частого** | Термін `rare` ($df = 2$) проти `common` ($df = 91$) в одному документі при $tf = 1$ | `score("rare") = 3.9512` > `score("common") = 0.0984` | Завдяки множнику $IDF = \ln(N / df)$ рідкісні слова інформативніші й дають у ~40 разів більший внесок у рейтинг. |
| **2** | **20-те повторення майже нічого не додає** | Документи однакової довжини з $tf = 1$, $tf = 10$ та $tf = 20$ для слова `target` | $tf = 1 \rightarrow \mathbf{2.3401}$, $tf = 10 \rightarrow \mathbf{5.1482}$, $tf = 20 \rightarrow \mathbf{5.4496}$ | Завдяки гіперболічному насиченню $\frac{tf \cdot (k_1 + 1)}{tf + k_1 \dots}$ перехід від 10 до 20 повторень додає лише **+5.8%** балів (асимптота $k_1 + 1 = 2.5$). |

## Відверто про обмеження поточної архітектури

1. **Індекс повністю розташовується в оперативній пам'яті (In-Memory Index):** На повному корпусі Вікіпедії (866 898 документів) завантаження індексу `index.bin` (`403.38 MB`) зі словниками та Python-об'єктами `Posting` потребує **5 456.4 MB RAM** і ~183 с на повний цикл холодного завантаження. Перехід на масиви `array('I')` / `np.int32` у Лабі 8 зменшує витрати пам'яті на постінги у ~3.9 раза (`з 24.13 MB до 6.22 MB` на 10 000 статей), проте для корпусів у десятки мільйонів документів знадобиться `numpy.memmap` та бітове стиснення списків постінгів (VarByte / SIMD-BP128).
2. **Точний перебір ембедингів (Flat Cosine Search без ANN-індексу):** Семантичний пошук виконує точне множення матриці всіх чанків на вектор запиту (`embeddings @ q_vec`). На десятках тисяч фрагментів це займає лічені мілісекунди, але при масштабуванні понад $10^6$ чанків лінійний перебір $O(N \cdot d)$ стане вузьким місцем і потребуватиме наближеного індексу (HNSW / FAISS).
3. **Статичний індекс без інкрементальних оновлень у реальному часі:** Додавання нових документів вимагає перебудови `index.bin` та `.npy`-матриць і перезапуску воркерів (немає LSM-сегментів, як у Lucene).
4. **Токенізація без морфологічної лематизації:** Токенізатор приводить текст до нижнього регістру через `casefold()` та нормалізує Unicode (`NFC`), але не виконує стемінгу чи лематизації для української мови (цю прогалину частково компенсують семантичний та гібридний режими).

## Швидкий старт та основні команди CLI

```bash
# 1. Встановлення залежностей
uv sync --dev

# 2. Обхід сайту асинхронним краулером
uv run findex crawl http://quotes.toscrape.com/ --max-pages 200 --concurrency 5 --out data/crawl.jsonl

# 3. Побудова інвертованого індексу та векторних ембедингів
uv run findex index data/crawl.jsonl index.bin
uv run findex embed index.bin --model all-MiniLM-L6-v2

# 4. Пошук у терміналі (режими: keyword, semantic, hybrid)
uv run findex search index.bin "київ AND україна" --mode keyword --scorer bm25
uv run findex search index.bin "головний мегаполіс нашої держави" --mode semantic
uv run findex search index.bin "київ столиця" --mode hybrid

# 5. Запуск вебсервера FastAPI
uv run findex serve --port 8000 --workers 1

# 6. Запуск перевірок, тестів та бенчмарків
uv run ruff check .
uv run pyright
uv run pytest tests/ --cov=src
```
