## Перевірка `sys._is_gil_enabled()` та гонитва даних (Race Condition)

Під час запуску на стандартному інтерпретаторі та на free-threaded збірці `Python 3.13t`:
```text
$ uv run python -c "import sys; print('GIL enabled:', sys._is_gil_enabled())"
GIL enabled: True

$ uv run --python 3.13t python -c "import sys; print('GIL enabled:', sys._is_gil_enabled())"
GIL enabled: False
```

**Гонитва даних (Race Condition) та її усунення:**
GIL захищає лише внутрішні C-структури самого інтерпретатора CPython (зокрема лічильники посилань), але **не захищає інваріанти програмної логіки**. Якщо кілька потоків одночасно оновлюють спільний `Counter` або список постінгів (`shared_index.postings[term].append(posting)` чи `counter[term] += 1`), між читанням старого значення і записом нового потік може бути перерваний (особливо на `3.13t` без GIL, де потоки модифікують пам'ять одночасно на різних ядрах), через що частина оновлень втрачається.
**Фікс:** Замість блокування кожного слова м'ютексом (`threading.Lock`), який перетворив би паралельну роботу на послідовну, застосовано патерн **Map-Reduce без спільного мутабельного стану**: кожен воркер будує власний ізольований `partial_idx = Index()`, а головний потік послідовно зливає їх через `final_index.merge(p)`.

## Аналіз: GIL, процеси, закон Амдала та Python 3.13t

1. **Чому потоки під GIL не прискорили індексацію:**
   Індексація тексту (Unicode NFC нормалізація, `casefold()`, пошук токенів регулярним виразом `re.finditer` та побудова об'єктів `Posting`) — це суто **CPU-bound** робота у Python-байткоді. Оскільки GIL дозволяє виконувати байткод лише одному потоку в конкретний момент часу, запуск 2–12 потоків не задіює додаткові ядра процесора, а лише додає накладні витрати на боротьбу за блокування (lock contention) і перемикання контексту ОС. Тому прискорення тримається біля `0.93x – 1.07x`.

2. **Чому процеси прискорили роботу і чим це оплачено:**
   У `ProcessPoolExecutor` кожен дочірній процес має власний незалежний інтерпретатор і власний GIL, що дозволяє навантажити всі 6 фізичних ядер `Intel Core i5-11400F` паралельно і скоротити реальний час (`Wall Time`) з `27.22 с` до `14.11 с` (**1.93x**).
   * **Ціна за CPU Time:** Сумарний процесорний час усіх ядер зріс із `27.12 с` до `38.84 – 40.08 с`. Ця різниця пішла на ініціалізацію процесів через `spawn` та міжпроцесну передачу даних (`pickle.dumps` у воркері та `pickle.loads` у батьківському процесі) для десятків тисяч об'єктів `Posting`.
   * **Поведінка Peak RSS:** Завдяки розподілу роботи між дочірніми процесами та звільненню пам'яті після завершення чанків піковий RSS батьківського процесу знизився до `1099 MB` на 4–12 процесах, тоді як у багатопотоковому режимі вся купа всіх потоків живе в одному адресному просторі (`3000–4036 MB`).

3. **Де в часі `merge` видно закон Амдала і що змінилось на Python 3.13t:**
   За **законом Амдала**, прискорення $S(N) = \frac{1}{s + \frac{1 - s}{N}}$ впирається у частку послідовної роботи $s$. У нашій реалізації зі збільшенням числа воркерів час власне токенізації скорочується, проте зростає послідовна фаза: час `merge` збільшується з `0.36 с` до `0.71–0.90 с`, до чого додається послідовне зчитування результатів через IPC (`unpickle`) і фінальна серіалізація `save_index` на диск. У сумі неподільна послідовна частина займає ~35–40% часу виконання, що й формує горизонтальне плато на графіку біля позначки `~2.0x`.
   * **Що змінилось на Python 3.13t:** Із вимкненим GIL (`sys._is_gil_enabled() == False`) потоки `ThreadPoolExecutor` отримали справжній паралелізм на всіх ядрах процесора **без витрат на `spawn` та `pickle`**, оскільки об'єкти `Index` повертаються з потоків напряму через спільну пам'ять за вказівником. Це дозволило досягти найкращого часу серед усіх режимів — **12.99 с (прискорення 2.09x)**.

## Інструкція з запуску

### 1. Побудова індексу
```bash
# Багатопроцесорний запуск (типовий режим)
/usr/bin/time -v uv run findex index data/ index.bin --executor processes --workers 4

# Багатопотоковий запуск
/usr/bin/time -v uv run findex index data/ index.bin --executor threads --workers 8

# Послідовний запуск
/usr/bin/time -v uv run findex index data/ index.bin --executor serial --workers 1
```

### 2. Замір метрик (Wall time, CPU time, Peak RSS)
```bash
/usr/bin/time -v uv run findex index data/ index.bin --executor processes --workers 4
```

### 3. Тестування без GIL (Python 3.13t)
```bash
uv python install 3.13t
/usr/bin/time -v uv run --python 3.13t findex index data/ index.bin --executor threads --workers 8
```
