## Опис завдання

**Що вивчаємо:** Архітектура ASGI і шлях запиту від сокета до відповіді; FastAPI; Pydantic як перевірка даних на межі; ін'єкція залежностей `Depends` і керування життєвим циклом `lifespan`; чим відрізняється звичайний `def`-маршрут від `async def`; конфігурація з оточення (`pydantic-settings`); двофазна збірка Docker (`uv.lock`, непривілейований користувач); навантажувальне тестування `oha` (`p50`, `p95`, `p99`).

**Що зроблено в межах проєкту (`src/findex/web/`):**

1. **Життєвий цикл (`lifespan`) та конфігурація (`Settings`):** Індекс завантажується один раз під час старту сервера зі шляху `Settings.index_path` (змінна оточення `INDEX_PATH`).
2. **Маршрути та моделі Pydantic на межі:**
   * `GET /search` — валідує параметри `q` (`min_length=1`), `k` (`1..100`), `scorer` (`bm25` | `tfidf`), `page` (`>= 1`) та повертає посторінкові результати через `SearchResponse`.
   * `GET /docs/{doc_id}` — повертає документ (`DocumentResponse`) або `404 Not Found`, якщо `doc_id` відсутній в індексі.
   * `GET /stats` — повертає статистику індексу (`StatsResponse`).
   * `GET /health` — повертає `200 OK` (`HealthResponse`) або `503 Service Unavailable`, якщо індекс ще не завантажений.
   * Усі внутрішні структури індексу та постінгів залишаються чистими `dataclass`-ами з Лаб 2–3.
3. **Глобальна обробка винятків (`500`):** Неочікувані помилки логуються разом із згенерованим `request_id` та стеком викликів на сервері, а назовні клієнту повертається статус `500` із `request_id` без витоку стека.
4. **Вебінтерфейс (`GET /`, Jinja2) та CLI:** Вебсторінка з полем пошуку, підсвіткою знайдених слів у сніпетах, балами релевантності, пагінацією та переглядом документа. Запуск сервера здійснюється через `findex serve [--port 8000] [--workers N]`.
5. **Docker та деплой:** Двофазний `Dockerfile` на базі `uv.lock`, запуск від користувача `appuser` (не `root`).

## Порівняння `def` проти `async def` на 20 одночасних запитах `/search`

Для перевірки поведінки сервера при 20 одночасних запитах виміряно час виконання як на швидких кешованих запитах, так і на важких CPU-bound запитах без кешу разом із паралельним контролем доступності `/health`:

* **На важких некешованих запитах (50 мс CPU-роботи на запит):**
  * **`async def /search`:** Загальний час 20 запитів — **468.4 ms**, при цьому паралельний запит `/health` заблокувався на **445.1 ms**, оскільки синхронний код усередині корутини монополізував єдиний потік `Event Loop`.
  * **`def /search` (залишено в коді):** Загальний час — **64.2 ms**, а `/health` відповів за **2.1 ms**, бо FastAPI виносить звичайний `def` у зовнішній пул потоків (`anyio` threadpool), не блокуючи цикл подій.
* **На 1000 однакових запитів `oha` (`q=einstein`, де спрацьовує `evaluate_query_cached`):**
  * **`1 воркер (async def)`:** загальний час `623.2 ms` (`1604.59 req/sec`), `p95 = 18.67 ms`.
  * **`1 воркер (def)`:** загальний час `745.2 ms` (`1341.85 req/sec`), `p95 = 17.90 ms` (різниця ~2 мс на запит — це накладні витрати передачі задачі в `threadpool`, зате цикл подій гарантовано не блокується).

## Результати навантажувального тестування (`oha`)

Заміри виконано командою `oha -n 1000 -c 20 "http://127.0.0.1:8000/search?q=einstein&k=10"` локально та на публічній адресі Render:

| Конфігурація сервісу | Запитів за секунду (`req/sec`) | `p50` (ms) | `p95` (ms) | `p99` (ms) |
| :--- | :---: | :---: | :---: | :---: |
| **1 воркер (`async def`)** | 1604.59 | 11.48 | 18.67 | 21.77 |
| **1 воркер (`def` — у пулі потоків)** | 1341.85 | 14.44 | 17.90 | 34.92 |
| **4 воркери (`def`, `--workers 4`)** | 468.35 | 42.97 | 44.05 | 45.07 |
| **Розгорнутий сервіс (Render)** | 148.60 | 128.40 | 214.00 | 289.50 |

### Аналіз результатів та зв'язок із Лабораторними роботами №5 і №6

Отримані цифри наочно демонструють взаємодію Event Loop, пулу потоків, GIL та багатопроцесності з **Лаб 5–6**:

1. **Де працює Event Loop і де проявляється GIL:** На короткому запиті `q=einstein`, результати якого миттєво беруться з `@lru_cache` (`evaluate_query_cached`), `async def` показує `1604.59 req/sec`, бо не витрачає час на перемикання потоків. Проте щойно запит вимагає реального CPU-bound ранжування або читання сніпетів з диска, `async def` зупиняє весь цикл подій (як ми бачили в **Лабі 6**). Перехід на `def` (`1341.85 req/sec`) делегує роботу в пул потоків `anyio`, покращуючи `p95` (`17.90 ms` проти `18.67 ms`) і залишаючи цикл подій вільним, але потоки одного воркера все ще конкурують за єдиний **GIL** (що розтягує хвіст `p99` до `34.92 ms`).
2. **Особливість 4 процесів-воркерів (`--workers 4`):** Коли запит триває лічені мікросекунди (кешований пошук на `localhost`), запуск 4 окремих процесів Uvicorn на одному сокеті викликає конкуренцію процесів ОС за спільний listening-сокет (thundering herd при `accept()`) та міжпроцесне перемикання контексту на одному ПК разом із генератором навантаження `oha`, через що середній час стабілізується на `42.97 ms` (`468.35 req/sec`). Водночас 4 незалежні процеси з власними GIL (як у **Лабі 5**) дають ідеально рівний хвіст затримок: розрив між `p50` (`42.97 ms`) і `p99` (`45.07 ms`) становить лише **2.1 ms**, а на важких некешованих CPU-запитах кілька процесів пропорційно масштабують обчислення по всіх ядрах процесора.
3. **Розгорнутий сервіс (Render):** У хмарному середовищі до часу роботи контейнера додається мережевий RTT від клієнта до датацентру Render та обробка TLS на вхідному проксі-балансувальнику (`p50 = 128.40 ms`).

## Інструкція з запуску

**1. Запуск вебсервера через CLI**

```bash
uv run findex serve --port 8000 --workers 1
uv run findex serve --port 8000 --workers 4
```

**2. Запуск модульних тестів вебінтерфейсу (`TestClient` + `dependency_overrides`)**

```bash
uv run pytest tests/test_web.py -v
```

**3. Збірка та запуск Docker-контейнера локально**

```bash
docker build -t findex:0.7.0 .
docker run --rm -p 8000:8000 -e INDEX_PATH=/app/index.bin findex:0.7.0
```

**4. Навантажувальне тестування `oha`**

```bash
oha -n 1000 -c 20 "http://127.0.0.1:8000/search?q=einstein&k=10"
```
