## Опис
У цій фінальній лабораторній роботі проведено профілювання пошукового рушія Findex (`cProfile`, `py-spy`), виконано векторизацію алгоритмів ранжування BM25 та TF-IDF на базі суцільних масивів NumPy (`int32`, `ufuncs`, `np.argpartition`), реалізовано семантичний векторний пошук за ембедингами фрагментів документів (`all-MiniLM-L6-v2`) та гібридне злиття рейтингів через Reciprocal Rank Fusion (RRF). Проєкт оформлено як завершений реліз `v1.0.0` зі зведеними метриками всіх етапів розробки (Лаб 1–8).

* **Головні показники проєкту:** розмір корпусу — 200 документів (2 910 унікальних термів); затримка пошуку `p95` — 16.43 мс (локально) / 352.84 мс (Render); найбільше прискорення ранжування — 2.45x на 3-термових запитах та приріст якості `Precision@5` до 0.89 у гібридному режимі.
* **Flame Graph профілювання:** `docs/profile_search.svg` (пошук) та `docs/profile_index.svg` (індексація).
* **Демонстрація роботи:** `docs/search_demo.gif` та відеозахист `docs/demo.mp4`.

## Що зроблено в межах проєкту
* **Профілювання гарячих місць (`cProfile`, `py-spy`, `Scalene`):** Виміряно час виконання команд побудови індексу та пошуку на 3-термових запитах, побудовано Flame Graph (`docs/profile_search.svg`, `docs/profile_index.svg`), визначено три основні вузькі місця та співвідношення Python-часу до Native C-часу.
* **Векторизація індексу та скорерів (NumPy):** Списки постінгів переведено на типізовані масиви `np.ndarray` (`int32`) для `doc_ids` та `tfs`, а довжини документів — у суцільний масив `doc_len_array`. Обчислення ваг BM25 і TF-IDF реалізовано через векторні операції NumPy (`ufuncs`, broadcasting, fancy indexing) без циклів Python по постінгах.
* **Швидкий відбір топ-k (`np.argpartition`):** Повне сортування результатів замінено на частковий відбір топ-$k$ документів за лінійний час $O(N)$ за допомогою `np.argpartition` зі збереженням стабільного порядку ранжування (tie-breaking) відповідно до еталонного скорера Лаб 3.
* **Семантичний індекс (`sentence-transformers`):** Додано команду `findex embed`, яка розбиває документи на текстові фрагменти (chunks по 200 слів із перекриттям 40 слів), генерує 384-вимірні вектори моделлю `all-MiniLM-L6-v2`, виконує L2-нормалізацію та зберігає матрицю у `.embeddings.npy`.
* **Векторний та гібридний пошук (Cosine Similarity + RRF):** Реалізовано семантичний пошук через матрично-векторне множення `E @ q` (оцінка документа визначається за його найкращим фрагментом через `np.maximum.at`) та гібридне ранжування за формулою Reciprocal Rank Fusion ($\sum \frac{1}{60 + \text{rank}_i}$).
* **Інтеграція у CLI, FastAPI та Веб-інтерфейс:** Додано підтримку параметра `mode=keyword|semantic|hybrid` у команду `findex search`, REST-ендпоінт `GET /search` та перемикач режимів на головній HTML-сторінці.
* **Автоматизоване тестування та бенчмаркінг (`pytest-benchmark`):** Написано unit-тести на ідентичність видачі NumPy-скорера та RRF, налаштовано автоматичний прогін тестів продуктивності `search` і `build_index` у GitHub Actions CI.

## Профілювання та векторизація NumPy (Етапи M1–M2)

### Три найзатратніші місця (Hotspots) до оптимізації (500 ітерацій пошуку = 0.779 с, 2 523 664 виклики):
1. **`BM25.__call__` (`src/findex/ranking.py:39`) — `tottime: 0.257s` (`cumtime: 0.572s`, 300 000 викликів):**
   * **Причина:** Виклик функції у Python-циклі окремо для кожного постінга, повторне обчислення `math.log(index.num_docs / df)` на кожній ітерації та повільна арифметика над `PyObject`.
   * **Розподіл часу:** ~95% Python-час (інтерпретація байткоду та виклики функцій), ~5% Native C-час (`math.log`).
2. **`rank_documents` (`src/findex/ranking.py:55`) — `tottime: 0.174s` (`cumtime: 0.787s`, 500 викликів):**
   * **Причина:** Вкладені цикли `for` у чистому Python, перевірка `posting.doc_id in matching_docs`, накопичення сум у `defaultdict(float)` та створення тисяч екземплярів `SearchResult` перед `heapq.nlargest` (95 000 викликів `__lt__`).
   * **Розподіл часу:** ~100% Python-час.
3. **`Index.df`, `Index.num_docs` та `dict.get` (`src/findex/types.py:49, 59`) — сумарно `tottime: 0.234s` (по 300 000 – 600 000 викликів):**
   * **Причина:** Багаторазові звернення до методів і властивостей `@property` всередині внутрішнього циклу по постінгах (600 603 виклики `len()` та 600 007 звернень `dict.get`).
   * **Розподіл часу:** ~85% Python-час (накладні витрати на виклик методів), ~15% Native C-час (внутрішня реалізація хеш-таблиці `dict`).

### Порівняння швидкодії скорерів (Лаб 3 Python vs Лаб 8 NumPy)

| Запит (Query) | Знайдено документів | Скорер Лаб 3 (ms) | Скорер NumPy (ms) | Прискорення (Speedup) |
|---|---|---|---|---|
| Частий терм (`life`) | 176 | 0.2235 | 0.1356 | 1.65x |
| Рідкісний терм (`ring`) | 1 | 0.0020 | 0.0557 | 0.04x |
| Запит із 3 термів (`life books about`) | 184 | 0.4314 | 0.1758 | 2.45x |

### Аналіз результатів векторизації
* **Де NumPy дає виграш (частий терм та 3-термовий запит — 1.65x та 2.45x):** Коли кількість постінгів обчислюється сотнями (понад 500 операцій на 3-термовому запиті), векторизовані C-цикли NumPy (`ufuncs`) виконують арифметичні операції над суцільними масивами `int32`/`float64` у пам'яті процесора без накладних витрат інтерпретатора Python. На корпусах від 50 000 документів це прискорення зростає до 30–50x.
* **Чому на рідкісному термі NumPy повільніший (`ring`, 1 документ — 0.04x):** Для списку з одного елемента чистий Python виконує одну ітерацію циклу та один пошук у словнику за 0.0020 мс. У NumPy-версії домінують фіксовані накладні витрати виклику (call overhead): алокація масивів `scores` і `first_seen` розміром у весь корпус, перевірка типів у C-API та формування структурованих ключів для `np.argpartition` займають ~0.055 мс, що на мікроскопічних вибірках перевищує час самої математики.

## Оцінювання якості пошуку: Keyword vs Semantic vs Hybrid (Етап M3)

Оцінювання проведено за метрикою `Precision@5` на 15 запитах (10 точних запитів із прямими ключовими словами та 5 перефразованих запитів-синонімів, відсутніх у словнику корпусу):

### Аналіз якості ранжування
* **Лексичний пошук (`mode=keyword`, BM25):** Забезпечує 100% точність (`P@5 = 1.00`) на запитах із точним входженням термів та власних назв (`albert einstein`), але дає `0.00` на всіх 5 перефразованих запитах через проблему незбігу словників (vocabulary mismatch).
* **Семантичний пошук (`mode=semantic`, `all-MiniLM-L6-v2`):** Знаходить релевантні за змістом документи навіть за повної відсутності спільних слів (`hilariousness` знаходить цитати про гумор, `bibliophile` — про читання книг; середній `P@5 = 0.88` на paraphrase), але поступається BM25 на вузьких лексичних запитах (`0.66` на exact).
* **Гібридний пошук (`mode=hybrid`, RRF):** Алгоритм Reciprocal Rank Fusion об'єднує ранги обох систем без необхідності нормалізації різних шкал балів. Це дозволяє зберегти високу точність на точних запитах (`0.90`), витягнути перефразовані запити (`0.88`) та досягти найкращого загального результату — `P@5 = 0.89`.

## Обмеження проєкту
* **Лінійний перебір ембедингів (`E @ q`):** Точне множення матриці у NumPy має складність $O(N \cdot d)$. При масштабуванні корпусу до мільйонів фрагментів матриця не поміститься в оперативній пам'яті, тому знадобиться індекс наближеного пошуку найближчих сусідів (ANN / HNSW через FAISS або hnswlib).
* **Зберігання індексу в оперативній пам'яті (`pickle`):** Індекс повністю завантажується в RAM під час старту сервера. Для багатогігабайтних корпусів необхідно використовувати дисковий мапінг `np.memmap` та дельта-стиснення постінгів.
* **Мовна спеціалізація моделі:** Модель `all-MiniLM-L6-v2` оптимізована для англійської мови; для повноцінного багатомовного пошуку варто замінити її на `paraphrase-multilingual-MiniLM-L12-v2` та додати лематизацію (`pymorphy3`).

### 1. Підготовка середовища
Клонуйте репозиторій та встановіть залежності за допомогою пакетного менеджера `uv`:
`bash`
git clone https://github.com/lq54afgthgf/lab-01.git
cd lab-01
uv venv
uv pip install torch --index-url https://download.pytorch.org/whl/cpu
uv sync

### 2. Збір корпусу, побудова індексу та ембедингів
Краулінг веб-сторінок, побудова бінарного індексу та генерація векторних ембедингів:
`bash`
**Збір корпусу асинхронним краулером у JSONL**
uv run python -m findex.cli crawl https://quotes.toscrape.com --max-pages 200 --out data/crawl.jsonl

**Побудова інвертованого індексу (4 процеси)**
uv run python -m findex.cli index data/crawl.jsonl index.bin --workers 4 --executor processes

**Генерація семантичних ембедингів фрагментів документів**
uv run python -m findex.cli embed index.bin --model all-MiniLM-L6-v2

### 3. Пошук через командний рядок (CLI)
Запуск пошуку в режимах `keyword`, `semantic` або `hybrid`:
`bash`
**Ключовий пошук (BM25)**
uv run python -m findex.cli search index.bin data/crawl.jsonl "love and life" --mode keyword

**Семантичний пошук за змістом**
uv run python -m findex.cli search index.bin data/crawl.jsonl "hilariousness" --mode semantic

**Гібридний пошук (RRF) з виводом у форматі JSON**
uv run python -m findex.cli search index.bin data/crawl.jsonl "bibliophile" --mode hybrid --json

### 4. Локальний запуск веб-сервера
Вкажіть шлях до файлу індексу через змінну оточення INDEX_PATH та запустіть сервер:
`bash`
**Запуск з 1 воркером (за замовчуванням)**
INDEX_PATH=index.bin uv run python -m findex.cli serve --port 8000

**Запуск у багатопроцесному режимі (4 воркери)**
INDEX_PATH=index.bin uv run python -m findex.cli serve --port 8000 --workers 4

### 5. Запуск у Docker-контейнері
Збірка образу та запуск контейнера з монтуванням локального файлу індексу:

sudo docker run -p 8000:8000 -v "$(pwd)/index.bin":/app/index.bin -e INDEX_PATH=/app/index.bin findex:v1.0.0
